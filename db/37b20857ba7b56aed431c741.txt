</h2><p>大致可以把rust中的宏看作是一种完善了C语言中宏种种弊端又添加了一些新特性的实现.</p>
<p>C语言中的宏是一种比复制粘贴稍微高明但有没那么高明的东西, 例如常见的 <code>#include</code> 宏将对应的文件递归复制并展开到当前文件, <code>#define</code> 宏将对应的占位符替换成对应的文本等等等. 这种设计颇有用 <code>sleep</code> 模拟异步的既视感, 其定义并没有一门编程语言那么精确.</p>
<p>这种简陋的设计也会带来很多与人第一感觉不同的结果, 例如最经典的<a href="https://doc.rust-lang.org/1.30.0/book/first-edition/macros.html#hygiene"target="_blank" rel="external nofollow noopener noreferrer">非预期宏</a>例子:</p>

</div><p>由于宏只是简单替换, 上述语句会变成 <code>5 * 2 + 3</code>, 最后结果是 <code>13</code> 而并不是期望的 <code>25</code>.</p>
<p>Rust的宏做了很多改进, 一个最经典的形容是 <em>hygenic</em> (干净的). 这一节在<a href="https://doc.rust-lang.org/1.30.0/book/first-edition/macros.html#hygiene"target="_blank" rel="external nofollow noopener noreferrer">Rust的文档</a>中就有单独介绍. 在设计上, 文档里有这么一句话:</p>
<blockquote>
<p>Each macro expansion happens in a distinct ‘syntax context’, and each variable is tagged with the syntax context where it was introduced.</p></blockquote>
<p>如果将上面的C语言代码用rust宏重新实现, 那么在宏调用中的语句 <code>2 + 3</code> 会被当成一个单独的表达式来对待, 而不仅仅只是替换.</p>
<p>除此之外, rust的宏可以和编译之后的object一起分发 (C语言的宏预处理完就没了) , 还支持 <a href="https://doc.rust-lang.org/book/ch19-06-macros.html#attribute-like-macros"target="_blank" rel="external nofollow noopener noreferrer">Attribute Like</a>、 <a href="https://doc.rust-lang.org/book/ch19-06-macros.html#function-like-macros"target="_blank" rel="external nofollow noopener noreferrer">Function Like</a> 等多种使用方式和特性, 也支持可变参数列表 (这个在Rust的function里还不支持) .</p>

</h2><p>与 C/C++ 一样, <code>macro</code> 是在编译期进行检查和展开的.</p>
<p>但是Rust利用编译期展开这个特性, 针对一些语言设计上的不安全隐患进行了改善. 例如pwn👴闭着眼睛都能利用的格式化字符串漏洞, 是由于 <code>printf</code> 函数是在运行时进行字符串构建并且并没有对参数进行严格检查导致的. Rust设计的 <code>print!</code> 宏就可以避免这一点. 宏通过编译时展开, 在编译期就可以得知参数数量是否匹配、变量是否有效、第一个参数是否是合法字符串字面值等等, 然后就可以直接解决格式化字符串不安全的问题.</p>
<p>而 <code>function</code> 的概念就和其他语言差不多了, 但是 Rust 的函数限制稍多, 不支持可变参数、不支持函数重载 (运算符是可以重载的) 、不支持给参数设置默认值等等等…… 而官方给出的理由是通过 Rust 编写程序的时候即使不使用这些奇怪的、可能导致不安全行为的特性, 也能够以另一种优雅的方式实现需求.</p>
<p><code>macro</code> 与 <code>function</code> 的一个主要区别就是, <code>macro</code> 不进行参数<del>评估</del><em>求值</em> (Evaluate) ——或者说直到代码中使用时才会对参数进行<em>求值</em> (Evaluate) .</p>
<p>这里的 “求值” 稍稍抽象, 可以这么解释:</p>
<p>比如说你调用函数的时候这么写: <code>hello(world(123))</code>, 程序会先对 <code>world(123)</code> 进行求值, 然后再将结果代入 <code>hello</code> 函数进行下一步处理. 这里先求值 <code>world(123)</code> 即为 <em>求值 (Evaluate)</em>. 而在 <code>macro</code> 中, 参数是作为一个表达式实体传进去的, 在宏中的代码调用之前, 这个表达式并不会被执行.</p>

</div><p>显然 <code>expr</code> 是没有一个合适类型声明的, 同时 <code>expr</code> 在传入之前就会被执行求值, 传进去的仅仅只是一个值而不是表达式, 我们就没办法实现宏中 <code>stringify!($cond)</code> 这样的功能.</p>
<p>除此之外, 一些类似 <code>printf</code> 之类需要进行不安全构造操作或者需要可变函数参数长度的功能也可以抽象成宏来使用.</p>
<p>使用宏还有一个好处, 就是宏中的部分计算都可以在编译期完成, 这样就可以实现一些类似于编译器打表的操作, 可以显著缩减运行时间.</p>
<p>一般的经验法则是, 在函数不能提供所需解决方案的情况下, 在你有相当重复的代码的情况下, 或者在你需要检查类型的结构并在编译时生成代码的情况下, 可以使用宏. 在能够使用函数的场景下还是要尽量使用函数.</p>
<p>宏由于对参数不做限制, 滥用可能会导致项目代码以后会很难以维护, 项目的可读性也会成倍增加. 另外, 宏是在编译期展开的, 也就意味着会有非常多的重复代码片段在展开时被插入到代码中, 这可能会影响CPU指令缓存, 从而导致性能下降.</p>
